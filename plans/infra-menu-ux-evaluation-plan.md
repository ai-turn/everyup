# 인프라 메뉴 UI·UX 평가 계획

작성일: 2026-11-11 · 상태: 약식 점검 완료 → [점검 결과](infra-menu-ux-evaluation-results.md) · 기준 HEAD `4594fe8b`

인프라 메뉴에서 **어떤 서버에 문제가 있는지 바로 찾을 수 있는가**, **자원 사용량과 추이를 오해 없이 읽을 수 있는가**를 평가한다. 로그 메뉴 평가([계획](log-menu-ux-evaluation-plan.md)·[결과](log-menu-ux-evaluation-results.md))와 같은 방식으로 채점하고, 이번에는 채점 뒤에 **더 나은 UI 구성안을 찾는 단계**를 추가한다.

인프라는 2026-10-31에 다른 제품과 비교하는 1차 점검을 마쳤다(PR #89). 이번 평가는 그때 다루지 않은 상태 표현·판독·키보드·모바일과, 화면 구성 자체를 바꿀 여지를 본다. 이번 단계에서는 제품 코드를 수정하지 않는다.

## 1. 평가 범위

기본 사용자는 CPU·메모리·디스크 사용률과 OpenTelemetry Collector를 아는 운영자이며, EveryUp 인프라 메뉴에는 익숙하지 않다고 가정한다.

| 페이지·화면 | 섹션 | 주요 컴포넌트·확인 대상 |
| --- | --- | --- |
| 인프라 목록 `/infrastructure` | L1. 제목과 연결 범위 안내 | PageHeader, MonitoringConnection(인프라 연결), DockerEnvironmentHint |
| 인프라 목록 | L2. 보기 전환 | ListViewToggle |
| 인프라 목록 | L3. 인프라 대상 | ResourceCard(이름·수집 상태·CPU/메모리/디스크), ResourceTable, `UsageValue`의 85% 위험 표시, 건수 |
| 인프라 목록 | L4. 빈·로딩·실패 상태 | 스켈레톤, EmptyState(미연결·실패·다시 시도) |
| 서버 상세 `/infrastructure/:id` | D1. 서버 정보와 연결 관리 | PageHeader, DirectConnectionMeta(수집 상태·마지막 수집·연결 방식·마스킹 키·그룹 배정) |
| 서버 상세 | D2. 기간과 페이지 액션 | DetailActionToolbar, TimeRangePicker, 새로고침, 알림 규칙, 삭제 |
| 서버 상세 | D3. 현재 사용량 게이지 | InfraGauges(VitalGaugeCard, 위험 표시, 부제) |
| 서버 상세 | D4. 사용량 추이 | InfraTrends 2×2(CPU·메모리·디스크 %, 네트워크 MB/s), 축·단위·범례·툴팁 |
| 서버 상세 | D5. 상세 상태 변형 | 상세 로딩·실패, 메트릭 없음·일부 누락, 메트릭만 실패 |
| 대화상자 | O1. Collector 연결 | InfrastructureCollectorSetupDialog → SetupResult(키, 주소, Docker·바이너리 실행 방식, 설정·명령 복사) |
| 대화상자 | O2. 관리 작업 확인 | 키 재발급·연결 중지·삭제 ConfirmDialog |
| 대화상자 | O3. 새 키 안내 | InfrastructureCollectorKeyDialog |

1차 점검에서 미룬 항목도 확인 대상에 넣는다: Collector 호스트의 CPU 코어 수, 디스크 마운트포인트 라벨, `docs/index.md` 스크린샷과 대체 텍스트.

Docker 환경 상세 안의 호스트 메트릭은 이번 범위에서 제외한다. 다만 같은 컴포넌트(InfraGauges·InfraTrends)를 쓰므로, 발견한 문제가 그쪽에도 영향을 주면 영향 화면으로 기록한다.

## 2. 채점 기준

로그 평가 계획의 §2 기준과 §3 집계 방식을 그대로 쓴다. 두 메뉴의 점수를 나란히 비교할 수 있게 하기 위해서다.

- 축: 직관성 40%, 가독성 40%, 상태·피드백 10%, 조작·일관성 10%. 각 1~5점.
- 환산식: `100 × Σ(비중×점수) ÷ (5 × Σ적용 비중)`. 적용되지 않는 축은 `N/A`, 확인하지 못한 항목은 `미검증`.
- 섹션 점수는 평가 단위 평균, 페이지 점수는 섹션 평균. 환경별 점수는 섞지 않고 나란히 표시한다.
- 심각도: S1 표현 개선, S2 작은 과업 방해, S3 큰 혼동·우회, S4 과업 차단·중대한 결과 오해.

인프라에 맞춰 가독성 판단에 두 가지 질문을 추가한다.

- 위험 수준(85% 이상)인 값이 색 외의 단서로도 구분되는가?
- 게이지의 현재 값과 추이 차트의 마지막 값이 같은 시점·같은 의미로 읽히는가?

## 3. 실제로 수행할 과업

| ID | 과업 | 확인할 내용 |
| --- | --- | --- |
| T1 | 목록에서 자원이 부족한 서버를 찾아 상세로 이동 | 위험 값의 발견 가능성, 카드·표의 비교 용이성, 수집 지연과 자원 위험의 구분, 복귀 |
| T2 | 상세에서 현재 상태와 최근 추이를 파악 | 게이지와 차트의 관계, 단위, 기간 변경 결과, 값이 없는 지표의 의미 |
| T3 | 차트에서 특정 시점의 값을 확인 | 툴팁, 여러 시리즈 구분, 키보드 접근, 기간별 밀도 |
| T4 | 수집이 끊긴 서버를 알아보고 원인을 추정 | 수집 중·지연·대기·중지의 구분, 마지막 수집 시각, 다음 행동 |
| T5 | 처음 서버를 연결하고 데이터가 들어오는지 확인 | 빈 목록에서 진입, 실행 방식 선택, 설정·명령 복사, 키 발급과 실제 수신의 구분 |
| T6 | 그룹·키·연결 상태를 관리하고 알림 규칙으로 이동 | 저장 결과, 재발급·중지·삭제의 영향과 취소, 알림 규칙 화면의 대상 유지 |

과업별로 예상 동작, 실제 경로, 추가 탐색, 완료 여부를 기록한다. 소스를 아는 평가자가 진행하므로 신규 사용자의 성공률로 해석하지 않는다.

## 4. 환경과 상태 표본

| 구분 | 계획 |
| --- | --- |
| 기준 실행 | 현재 작업트리의 로컬 데모(`build:demo`). 커밋·포트·브라우저 버전을 기록하고, 4173/4174를 다른 worktree가 쓰고 있으면 별도 포트를 쓴다 |
| 기본 화면 | 데스크톱 1440×900, 모바일 390×844, 각각 라이트·다크 |
| 좁은 화면·확대 | 320px 폭, 루트 글자 200% (라이트) |
| 기본 데이터 | 정상 서버, 85% 이상 값이 있는 서버, 카드·표 보기 |
| 빈·누락 상태 | 미연결, 키만 발급하고 수신 없음, 메모리·디스크 미전송(`-`), 네트워크만 없음 |
| 실패·진행 | 목록·상세 실패, 메트릭만 실패, 그룹 저장 실패, 연결·관리 처리 중 |
| 정보 경계 | 긴 서버명, 100%·0%, 큰 네트워크 값, 수집 지연·중지 |
| 입력 방식 | 마우스, Tab·Enter·Space·Escape, 모바일 터치 에뮬레이션 |

실패·경계 상태는 로그 평가 때처럼 평가용 브라우저의 응답 대체로 재현하고, 자연 발생 상태와 구분해 기록한다.

## 5. UI 개선안 탐색 (이번에 추가하는 단계)

채점이 "현재 화면이 얼마나 좋은가"를 본다면, 이 단계는 "화면 구성을 바꾸면 더 나아지는가"를 본다. 지금 구조 안에서 고치는 수정과 구조를 바꾸는 대안을 구분해 제시한다.

**대상 선정.** 다음 중 하나에 해당하는 섹션만 대안을 찾는다. 모든 섹션에 대안을 만들지 않는다.

- 섹션 점수가 80점 미만이다.
- S2 이상 이슈가 있고, 현재 구조 안의 수정으로는 해결되지 않는다.
- 과업 T1·T2(문제 서버 찾기, 상태 파악)에 직접 관련된다. 인프라 메뉴의 핵심 가치이므로 점수와 관계없이 본다.

**참고 제품.** 1차 점검의 비교 대상(SigNoz `InfraMonitoringHostsV2`, Beszel `systems-table`, Checkmate `Infrastructure`)에 더해, 상세 화면 구성은 Netdata와 Grafana Node Exporter 대시보드를 본다. 소스나 공개 데모의 구성 방식만 참고하고 모양을 그대로 옮기지 않는다.

**미리 떠올린 질문.** 채점 결과에 따라 버리거나 추가한다.

- 목록: 숫자 세 개 대신 사용률 막대나 짧은 추이(sparkline)가 위험 서버를 더 빨리 찾게 하는가? 서버가 많을 때 위험 순 정렬이 기본이어야 하는가?
- 상세: 게이지 카드와 2×2 차트가 같은 정보를 두 번 보여 주는가? 게이지를 차트 머리의 현재 값으로 합치면 첫 화면이 짧아지는가?
- 상세: 수집 상태와 연결 관리 정보가 첫 화면을 얼마나 차지하는가? 모바일에서 첫 지표가 어디서 시작하는가?
- 공통: 85% 한 단계만으로 충분한가, 주의 단계가 필요한가? (임계값 설정은 알림 점검으로 미룬 상태이므로 표시 방식만 본다.)

**형식.** 대안마다 다음을 적는다.

| 항목 | 내용 |
| --- | --- |
| 해결하는 이슈 | 이슈 ID와 과업 |
| 현재 vs 대안 | 같은 데이터로 그린 정적 시안 두 장 (평가 데모 데이터 사용) |
| 장점·비용 | 기대하는 행동 변화, 수정 규모 S/M/L, 백엔드 변경 여부, 다른 메뉴(로그·API·Docker 상세)와의 일관성 영향 |
| 기존 결정과의 충돌 | DESIGN.md·차트 스펙(2×2 유지, ChartCard, monotoneX 등)과 부딪히면 명시 |

시안은 HTML 정적 페이지로 만들고 제품 코드에 넣지 않는다. 기존 결정을 뒤집는 대안(예: 2×2 해체)은 채택 여부를 사용자에게 묻는 항목으로만 올린다.

## 6. 근거와 도구

로그 평가 계획 §6과 같다: Nielsen 사용성 원칙(질문 구성용), WCAG 2.2(대비·색 외 단서·키보드·리플로우·대상 크기), axe-core(후보 수집, 수동 확인), Playwright(재현·기록), `web/frontend/DESIGN.md`(프로젝트 규약). 로그 평가의 `audit.mjs`를 복사해 인프라 경로와 상태 주입만 바꿔 쓴다. 의존성은 추가하지 않는다.

## 7. 실행 순서와 완료 조건

1. **평가 단위 확정:** §1 섹션 아래 평가 단위에 ID를 붙이고 적용 축을 정한다.
2. **환경 준비:** 데모 빌드, 포트 확인, 증거 폴더 `plans/infra-menu-ux-evaluation-evidence/` 생성.
3. **과업·상태 점검:** T1~T6을 4개 환경에서 수행하고, 실패·경계 상태를 주입해 캡처한다.
4. **채점과 이슈 정리:** 단위 → 섹션 → 페이지 순으로 집계하고, 이슈에 심각도·수정 규모를 붙인다.
5. **개선안 탐색:** §5 기준으로 대상 섹션을 고르고 대안과 시안을 만든다.
6. **보고:** 결과 문서에 점수표·이슈·대안을 정리하고, 수정할 범위와 대안 채택 여부를 사용자와 정한다.

모든 평가 단위에 `검증 완료 / N/A / 미검증`이 표시되고, 대상으로 고른 섹션마다 "현재 구조 안의 수정"과 "구조 대안"(없으면 없다고)이 적혀 있으면 평가를 마친다. 실제 수정과 재채점은 그 뒤에 별도로 진행한다.
