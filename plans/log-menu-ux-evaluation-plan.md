# 로그 메뉴 UI·UX 평가 계획

작성일: 2026-11-08 · 상태: 채점 완료 → [평가 결과](log-menu-ux-evaluation-results.md)

로그 메뉴에서 **무엇을 확인하고 어디를 조작해야 하는지 쉽게 이해할 수 있는가**, **로그와 상태를 빠르고 정확하게 읽을 수 있는가**를 평가한다. 페이지 → 섹션 → 컴포넌트 순서로 결과를 볼 수 있게 하고, 각 점수에 관찰 근거와 개선안을 연결한다.

현재 소스에서 확인한 페이지는 `/logs`, `/logs/:serviceId` 두 개다. 계획 작성 시 HEAD는 `8aee82ef`이며, 실제 평가 때 커밋과 작업트리 변경 내역을 다시 기록한다. 이번 단계에서는 제품 코드 수정이나 실제 점수 산정을 하지 않는다.

## 1. 대상 사용자와 평가 범위

기본 사용자는 로그 레벨·시간 범위·서비스 개념을 아는 개발자 또는 운영자이며, EveryUp 로그 메뉴에는 익숙하지 않다고 가정한다. OpenTelemetry 연결 절차의 전문 용어는 필요한 설명과 다음 행동이 제공되는지 확인한다.

| 페이지·화면 | 평가할 섹션 | 주요 컴포넌트·확인 대상 |
| --- | --- | --- |
| 로그 목록 `/logs` | L1. 제목과 연결 범위 안내 | PageHeader, 로그 연결 버튼, DockerEnvironmentHint |
| 로그 목록 | L2. 보기 전환 | ListViewToggle, 카드·그리드 선택 표시 |
| 로그 목록 | L3. 로그 서비스 | LogServiceOverview, 서비스 카드·ResourceTable, 수집 상태, 오류·경고 수, 추이, 최근 메시지 |
| 로그 목록 | L4. 자주 발생한 오류·경고 | 패턴 메시지, 서비스명, 발생 횟수·시각, 상세 이동 |
| 서비스 상세 `/logs/:serviceId` | D1. 서비스 정보와 연결 관리 | PageHeader, DirectConnectionMeta, 수집 상태·마지막 수집, 마스킹된 키, 그룹 배정·저장 |
| 서비스 상세 | D2. 수집 레벨 설정 | LogIngestLevels, 선택·저장·적용 범위 설명 |
| 서비스 상세 | D3. 기간과 페이지 액션 | TimeRangePicker, 새로고침, 알림 규칙 이동, 삭제 |
| 서비스 상세 | D4. 로그 탐색 조건 | 조회 레벨, 메시지 검색, 속성·패턴·트레이스·시간 구간 필터, 조건 해제, 실시간 갱신 |
| 서비스 상세 | D5. 로그 발생량 | LogVolumeHistogram, 축·단위·범례, 툴팁, 구간 선택 |
| 서비스 상세 | D6. 로그 목록과 이동 | LogRow의 시간·레벨·메시지, 결과 건수, Pagination |
| 서비스 상세 | D7. 로그 행 펼침 | 전체 메시지, 속성·리소스, 속성 필터 적용, 원본 JSON |
| 서비스 상세 | D8. 트레이스 확인 | TracePanel 진입·닫기·로그 복귀, 키보드 포커스 |
| 로그에서 여는 대화상자 | O1. 로그 직접 연결 | DirectTelemetrySetupDialog, 새·기존 서비스 선택, 입력, 연결 결과·설정 안내 |
| 로그에서 여는 대화상자 | O2. 관리 작업 확인 | 키 재발급·연결 중지·삭제 ConfirmDialog, 영향 설명, 취소·진행 상태 |
| 로그에서 여는 대화상자 | O3. 새 키 안내 | RotatedTelemetryKeyDialog, 새 키 확인·설정 안내·닫기 |

컴포넌트는 사용자가 구별하고 조작하는 단위로 나눈다. 예를 들어 서비스 카드 하나에만 점수를 주지 않고, 수집 상태·오류 건수·추이·최근 메시지의 판독성도 구분한다. 같은 모양의 로그 행이나 서비스 카드 인스턴스마다 점수를 반복해서 부여하지 않는다.

목록·상세의 로딩, 오류, 빈 상태는 해당 섹션의 상태 변형으로 포함한다. 사이드바·브레드크럼은 로그 진입과 복귀에 영향을 주는 부분을 확인한다. Docker 환경 내부의 로그 탭과 설정 메뉴의 감사 로그는 별도 페이지 평가에 포함하지 않는다. Docker 안내와 알림 규칙 링크는 목적지와 맥락 연결까지 확인한다.

## 2. 평가 기준과 점수

직관성과 가독성에 전체 비중의 80%를 둔다. 아래 가중치와 환산식은 **프로젝트 목적에 맞춘 자체 기준**이다. 외부 표준 점수나 다른 제품과의 백분위로 해석하지 않는다.

| 평가 축 | 비중 | 판단 질문 |
| --- | ---: | --- |
| 직관성 | 40% | 화면 목적과 다음 행동이 보이는가? 버튼·아이콘·용어로 결과를 예측할 수 있는가? 설정과 조회 조건을 구분할 수 있는가? |
| 가독성 | 40% | 서비스·시각·레벨·메시지의 중요도를 구분할 수 있는가? 글자·행간·대비·밀도·줄바꿈이 판독을 돕는가? 차트의 값과 범위를 오해 없이 읽을 수 있는가? |
| 상태·피드백 | 10% | 적용된 조건, 수집·갱신·저장 상태가 보이는가? 데이터 없음·0건·수신 대기·실패를 구분하고 다음 행동을 알 수 있는가? |
| 조작·일관성 | 10% | 같은 역할의 조작과 표현이 일관되는가? 키보드·터치로 조작하고 닫기·해제·복귀할 수 있는가? |

직관성은 **행동 전의 이해·예측**, 상태·피드백은 **현재 상태와 행동 후의 결과 인지**를 중심으로 구분한다. 한 문제는 주된 평가 축에 배정하며, 다른 축에도 영향을 준다고 판단하면 별도 영향을 설명한다. 같은 문제를 이유 없이 여러 번 감점하지 않는다.

각 축은 다음 기준으로 1~5점을 부여한다. 체크리스트 항목 수를 기계적으로 감점하는 방식 대신, 관찰된 문제가 과업 이해와 완료에 주는 영향을 판단한다.

| 점수 | 판단 기준 |
| ---: | --- |
| 5 | 점검한 과업과 상태에서 의미·행동·결과가 명확하고 뚜렷한 마찰을 발견하지 못함 |
| 4 | 과업은 명확하게 완료할 수 있으나, 작은 판독·표현·조작 개선점이 있음 |
| 3 | 재독이나 추가 탐색이 필요하지만, 화면 안의 단서로 해결할 수 있음 |
| 2 | 반복 탐색·오해가 발생하기 쉬우며, 보충 설명이나 우회가 있어야 해결할 수 있음 |
| 1 | 핵심 정보를 판독하거나 과업을 완료하기 어렵거나, 실제 동작이 의도와 크게 어긋남 |

환산식은 `100 × Σ(적용 축의 비중 × 축 점수) ÷ (5 × Σ적용 축의 비중)`이다. 모든 축이 적용되면 `직관성×8 + 가독성×8 + 상태·피드백×2 + 조작·일관성×2`이며, 범위는 20~100점이다. 원래의 1~5점도 함께 표시한다.

특정 컴포넌트에 적용되지 않는 축은 `N/A`로 표시하고 적용 축의 비중만 재분배한다. 아직 확인하지 못한 항목은 `미검증`이며 N/A와 구분한다. 미검증 항목은 점수를 만들어 채우지 않고, 상위 점수에 검증 범위와 잠정 여부를 표시한다.

## 3. 집계와 개선 우선순위

- 컴포넌트는 축별 원점수·환산점수·근거를 기록한다. 섹션 점수는 그 안의 평가 단위 점수 평균, 페이지 점수는 섹션 점수 평균으로 계산한다. 평가 전에 단위 목록을 고정해 컴포넌트를 잘게 나누는 정도가 결과를 바꾸지 않게 한다.
- 대화상자는 연결·관리 흐름의 별도 점수표로 제시한다. 페이지의 진입 버튼 점수와 같은 대화상자 점수를 중복 집계하지 않는다.
- 공통 컴포넌트의 같은 문제는 이슈 하나로 관리하고 영향받는 화면을 연결한다. 사용 맥락·배경·배치가 다르면 해당 맥락의 점수를 따로 기록한다.
- 데스크톱·모바일, 라이트·다크의 점수는 나란히 표시한다. 환경을 섞은 평균으로 특정 환경의 문제를 감추지 않는다. 같은 환경에서 여러 상태를 확인한 경우, 축 점수는 재현된 가장 큰 과업 영향에 맞추고 상태별 근거를 남긴다.
- 총점 옆에는 핵심 과업의 차단 여부와 미검증 범위를 표시한다. 높은 평균이 과업 차단을 상쇄하지 않게 한다.

문제의 심각도는 품질 점수와 별도로 기록한다. Nielsen의 [사용성 문제 심각도 기준](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/)을 참고해 S1은 표현 개선, S2는 과업을 방해하는 작은 문제, S3은 큰 혼동·우회, S4는 과업 차단 또는 중대한 결과 오해로 구분한다. 이슈로 인정하지 않는 관찰은 S0으로 정리한다.

개선 순서는 심각도 → 핵심 과업 영향 → 영향받는 환경·화면 범위 → 반복 발생 여부로 정한다. 수정 규모는 S/M/L로 별도 표시하며, 실제 사용 빈도는 분석 데이터가 없는 한 추정치임을 밝힌다.

## 4. 실제로 수행할 과업

| ID | 과업 | 확인할 내용 |
| --- | --- | --- |
| T1 | 목록에서 확인할 서비스를 골라 상세로 이동 | 직접 연결·Docker 범위 이해, 수집 상태와 오류·경고 판독, 카드·그리드의 정보 차이, 복귀 |
| T2 | 반복 오류에서 해당 로그를 열고 조건 해제 | 패턴 의미, 서비스·기간·적용 조건의 연속성, 전체 조회로 돌아가는 방법 |
| T3 | 기간·레벨·메시지로 로그를 좁히고 해제 | 입력과 적용 시점, 활성 조건, 복합 조건의 결과, 검색 결과 없음에서 회복 |
| T4 | 발생량 차트에서 특정 시간 구간 조사 | 축·단위·레벨 구분, 구간 선택의 발견 가능성, 선택 표시·해제 |
| T5 | 로그 전문·속성·JSON·트레이스를 확인하고 복귀 | 긴 내용 판독, 속성 필터, 행 펼침과 내부 버튼 구분, 패널 닫기·포커스 복귀 |
| T6 | 실시간 조회와 과거 페이지 탐색 | 갱신 켜짐·꺼짐, 갱신 주기 안내, 페이지 이동 시 상태 변화, 읽던 내용의 안정성 |
| T7 | 처음 로그를 연결하고 다음 단계를 이해 | 빈 목록에서 진입, 새·기존 서비스, 입력 오류, 키 발급과 실제 로그 수신의 구분, 설정 안내 |
| T8 | 수집 설정·그룹·키·연결 상태 관리 | 수집 레벨과 조회 필터의 차이, 적용 대상·시점, 저장 결과, 재발급·중지·삭제의 영향과 취소 |

과업별로 예상 동작, 실제 경로·결과, 추가 탐색·되돌리기, 완료 여부를 기록한다. 소스를 아는 평가자가 진행하므로 이 기록을 신규 사용자의 성공률·이해도·수행 시간으로 해석하지 않는다. 실제 사용자 조사가 없는 상태에서 SUS 등 사용자 설문 점수를 대신 산출하지 않는다.

## 5. 환경과 상태 표본

| 구분 | 계획 |
| --- | --- |
| 기준 실행 | 현재 작업트리의 로컬 데모. 커밋·변경 파일·시작 URL·브라우저 버전을 기록 |
| 기본 화면 크기 | 데스크톱 1440×900, 모바일 390×844, 각각 라이트·다크 |
| 좁은 화면·확대 | 320 CSS px 폭, 글자 200% 확대에서 목록·필터·로그 전문·대화상자의 손실과 가림 확인 |
| 기본 데이터 | 오류·경고가 있는 상태와 정상 상태, 카드·그리드 보기 |
| 빈 상태 | 미연결, 기간 내 수신 없음, 조건에 맞는 로그 없음 |
| 실패·진행 상태 | 최초 로딩, 목록·상세 실패, 반복 패턴만 실패, 설정 조회·저장 실패, 연결·관리 처리 중 |
| 정보 경계 | 긴 서비스명·메시지·속성·JSON, 큰 건수, 트레이스 유무, 수집 대기·지연·중지 |
| 입력 방식 | 마우스, Tab·Enter·Space·Escape, 모바일 터치 에뮬레이션 |

기본 과업은 네 환경 조합에서 확인하고, 실패·경계 상태는 먼저 데스크톱 라이트에서 확인한다. 레이아웃·색·터치·포커스에 영향을 주는 변형은 관련 환경에서 추가 확인한다. 전 조합을 확인하지 않은 상태는 점검 범위를 명시한다.

상태는 기존 데모 시나리오를 우선 사용한다. 부족한 실패·경계 데이터는 평가용 브라우저의 응답 대체 등으로 재현하고, 자연 발생 상태와 주입 상태를 구분한다. 데모에서 상태를 선택했다는 이유만으로 해당 API 실패가 재현되었다고 판단하지 않는다. 연결·설정 변경은 데모 또는 격리된 평가 데이터로 확인한다.

## 6. 근거와 도구의 역할

| 근거·도구 | 사용할 목적 | 해석 범위 |
| --- | --- | --- |
| [Nielsen의 10가지 사용성 원칙](https://www.nngroup.com/articles/ten-usability-heuristics/) | 익숙한 용어, 예측 가능한 조작, 기억 부담, 오류 회복 등을 점검하는 질문 구성 | 자체 가중치의 출처나 자동 채점표로 사용하지 않음 |
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | 글자·컨트롤 대비, 색 외 상태 단서, 키보드·포커스, 리플로우 점검 | 관련 기준을 개별 확인하며 전체 접근성 준수를 인증하는 점검으로 해석하지 않음 |
| GitHub [dequelabs/axe-core](https://github.com/dequelabs/axe-core/blob/develop/README.md) | 접근성 자동 검사로 대비·이름·구조 문제 후보 수집 | 자동 판정이 불확실한 항목은 수동 확인. 직관성이나 전체 UX의 점수로 변환하지 않음 |
| 저장소의 Playwright 구성과 [로그 E2E](../web/frontend/e2e/logs.spec.ts) | 이동·필터·키보드 동작 재현, 화면·DOM·조작 기록 수집 | 기능 테스트 통과를 사용성 우수로 해석하지 않음 |
| [프로젝트 디자인 규약](../web/frontend/DESIGN.md) | 정보 밀도, 타이포그래피, 상태 표현, 모바일 조작 크기의 프로젝트 기준 확인 | 규약 준수와 실제 판독·조작 품질을 함께 판단 |

일반 텍스트 대비 4.5:1, 큰 텍스트 3:1을 실제 전경·배경 조합에서 확인한다. [WCAG 텍스트 대비 기준](https://www.w3.org/TR/WCAG22/#contrast-minimum)에 따른다. 포인터 대상 최소 크기 24×24 CSS px는 간격·인라인 등의 예외까지 확인하고, 프로젝트의 모바일 컨트롤 높이 44px 규약과 구분한다. [WCAG 포인터 대상 크기 기준](https://www.w3.org/TR/WCAG22/#target-size-minimum)을 참고한다. 차트·표·원본 JSON처럼 이차원 배치가 필요한 영역은 [320px 리플로우 기준의 예외](https://www.w3.org/TR/WCAG22/#reflow)와 실제 사용 가능성을 따로 판단한다.

글자가 작다는 사실만으로 감점하거나, 운영 화면 전체에 큰 글씨·낮은 밀도를 일괄 요구하지 않는다. 메시지·숫자·시간·상태를 실제 크기에서 구분하고 읽을 수 있는지를 확인한다.

기존 [첫 방문 UX 결과](first-visit-ux-audit-results.md), [디자인 점검](impeccable-hallmark-check.md), [수정·재검증 결과](ux-fixes-results.md)는 재확인할 경로와 조건을 찾는 데 사용한다. 과거 캡처나 수정 전 문제를 현재 점수 근거로 그대로 옮기지 않는다. 점검 도구는 평가용 환경에서 사용하며 이번 계획 단계에 의존성을 추가하지 않는다.

## 7. 실행 순서와 완료 조건

1. **평가 목록 확정:** 위 섹션 아래의 평가 단위, 적용 축, 필수 상태·과업을 목록화하고 식별자를 부여한다.
2. **환경 준비:** 로컬 데모의 기준 상태·기간·테마·뷰포트를 기록한다. 이전 캡처를 덮어쓰지 않는 별도 증거 폴더를 준비한다.
3. **기준 적용 확인:** 서비스 카드·필터·로그 행에 같은 1~5점 기준을 적용해 본다. 기준에 모호함이 있으면 문구를 보완하고 채점 전에 고정한다. 나머지를 평가한 뒤 이 세 항목도 다시 확인한다.
4. **과업·상태 점검:** T1~T8을 수행하고 네 환경의 화면과 필요한 상태 변형을 기록한다. 자동 검사 후보는 실제 DOM·조작으로 확인한다.
5. **채점과 집계:** 컴포넌트 → 섹션 → 페이지 순으로 점수와 검증 범위를 집계한다. 동일 문제를 묶고 심각도·개선 순서를 정한다.
6. **보고:** 낮은 점수의 이유뿐 아니라 유지할 만한 점도 제시한다. 우선 개선 항목에는 기대하는 사용자 행동 변화와 재평가 조건을 적는다.

모든 평가 단위에 `검증 완료 / N/A / 미검증`이 표시되고, 점수가 있는 항목에는 근거가 연결되어야 한다. T1~T8의 결과와 미완료 사유, 환경별 검증 범위를 기록하면 평가 보고를 마친다. 이후 UI 수정과 재채점은 이 결과를 기준으로 별도 진행한다.
