# EveryUp 소개 페이지·데모 첫 방문 UX 점검 계획

작성일: 2026-11-07 · 계획 수립 시 확인한 로컬 커밋: `2d37ed3d`

처음 방문한 사람이 EveryUp의 용도를 이해하고, 데모에서 문제를 발견하고 살펴본 뒤, 실제 사용 방법까지 찾을 수 있는지 점검한다. 핵심은 가독성, 직관성, 탐색 흐름이다.

이 문서는 점검 계획이다. 스킬·플러그인 검색과 저장소의 화면 구성 확인을 마친 뒤 수립했다.
2026-11-07에 에이전트 실행 점검을 수행했으며 [결과 보고서](first-visit-ux-audit-results.md)에 근거와 개선 후보를 정리했다.
실제 신규 사용자 테스트는 아직 수행하지 않았다.

## 1. 대상과 범위

주 사용자는 웹 서비스나 서버를 운영하지만 EveryUp을 처음 접하는 개발자로 가정한다. 모니터링 경험이 적은 사용자와 다른 모니터링 도구를 사용해 본 사용자의 관점을 함께 검토한다.

| 대상 | 주소·범위 | 확인할 경험 |
| --- | --- | --- |
| 소개 페이지 | <https://ai-turn.github.io/everyup/> | 첫 화면, 기능 소개, 대표 이미지, 데모·시작하기 링크 |
| 데모 | <https://ai-turn.github.io/everyup/demo/> | 직접 진입과 소개 페이지 경유 진입, 개요, 메뉴, 주요 상세 화면 |
| 사용 시작 | 소개 페이지의 시작하기 → Quick Start | 설치 방식과 준비 조건을 이해하고 다음 행동을 찾는 지점까지 |

한국어 화면을 우선한다. 영어·한국어 혼용이 이해에 영향을 주는 부분은 포함한다. 백엔드 성능, 보안 구조, 실제 Collector 설치·수집 성공 여부는 이번 점검 범위에 포함하지 않는다.

배포 화면을 사용자 경험의 기준으로 삼고, 로컬 소스는 원인과 수정 위치를 찾는 데 사용한다. 배포 버전과 로컬 화면이 다르면 별도 기록하며 두 환경의 관찰을 합치지 않는다.

## 2. 활용할 스킬·플러그인

### 기본 조합

**브라우저에서 과업을 따라가며 관찰 → 문구 검토 → UI 기준과 코드 대조** 순서로 진행한다. 스킬은 점검 기준을, 브라우저 도구는 실제 화면과 동작 근거를 제공한다.

| 도구 | 확인된 상태 | 역할과 채택 판단 |
| --- | --- | --- |
| `toss-technical-writing` | 현재 세션에서 사용 가능 | 소개 문구, 제목, 메뉴 설명, 버튼 문구를 검토한다. 공개 토스 가이드를 재구성한 개인 스킬이며 토스 공식 배포 스킬은 아니다. 기본 사용. |
| `orca-cli`의 내장 브라우저 | 현재 세션에 스킬과 CLI 제공 | 배포·로컬 페이지의 실제 탐색, 화면·DOM 확인, 관찰 근거 수집에 사용한다. 실행 시 버전별 브라우저 가이드를 먼저 읽는다. 기본 사용. |
| Vercel `web-design-guidelines` | 외부 후보, 이번 작업에서 설치하지 않음 | 접근성, 포커스, 텍스트 처리, 내비게이션, 반응형 UI의 코드 점검에 적합하다. 기준 원문을 확인했으며 추가 스킬로 우선 추천한다. 사용자 이해 여부는 별도 관찰한다. |
| Anthropic `webapp-testing` | 외부 후보, 이번 작업에서 설치하지 않음 | Playwright를 통한 화면 캡처와 동작 재현을 지원한다. 프로젝트에 이미 Playwright가 있어 초기 점검의 필수 설치 대상은 아니다. 반복 재현이 필요할 때 선택한다. |
| Product Design 플러그인 | 검색 결과상 미설치, 설치 제안만 제공 | 카탈로그에 사용자 흐름 점검, 라이브 URL 기반 프로토타입 기능이 명시되어 있다. 개선 방향 비교와 시안 제작을 추가할 때 유용한 선택지다. 실제 도구의 품질·실행 결과는 아직 검증하지 않았다. |
| Figma 플러그인 | 검색 결과상 설치됨 | 개선안을 편집 가능한 화면으로 만들고 비교·공유할 때 선택한다. 1차 점검에는 필요하지 않다. |

기존 브라우저 도구와 문구 스킬만으로 점검을 시작할 수 있다. Product Design을 활용하려면 사용자의 설치가 필요하지만, 설치 여부가 기본 점검을 막지는 않는다.

2026-11-07 조회 당시의 수치이며, 인기도를 UX 점검 품질의 보증으로 사용하지 않는다.


플러그인은 현재 카탈로그 검색 결과를 근거로 선정했다. Product Design 외의 신규 브라우저 플러그인은 기존 도구와 역할이 겹쳐 기본 조합에 추가하지 않는다.

## 3. 다섯 가지 점검 기준

| 카테고리 | 확인할 질문 | 기록할 근거 |
| --- | --- | --- |
| 첫인상과 서비스 이해 | 무엇을 하는 서비스인가? 누구에게 유용한가? 셀프호스팅이라는 조건이 전달되는가? | 첫 화면 캡처, 주요 문구, 서비스 설명에 필요한 정보의 위치 |
| 시각적 가독성과 정보 위계 | 제목·핵심 수치·다음 행동이 구분되는가? 글을 읽는 순서가 자연스러운가? | 글자 크기·대비, 줄바꿈, 여백, 정보 밀도, 강조 요소의 경쟁, 차트 범례·단위 |
| 메뉴와 용어의 직관성 | 메뉴 이름으로 목적지를 예상할 수 있는가? 현재 위치와 돌아갈 경로가 보이는가? | 클릭 전 예상과 도착 화면의 차이, 그룹·Docker 환경·기능별 메뉴의 설명, 아이콘 라벨 |
| 데모 진입과 탐색 안내 | 예시 데이터임을 이해하는가? 처음 볼 대상과 클릭할 요소를 발견할 수 있는가? | 첫 진입 화면, 데모 안내 위치, 상태 선택기, 빈 화면 안내, 클릭 피드백 |
| 기능의 가치 전달과 다음 행동 | 장애를 발견하고 원인을 좁히는 과정을 경험하는가? 실제 사용 방법을 찾을 수 있는가? | 문제→상세→관련 데이터의 연결, 수치 해석, 데모 제약 안내, 시작하기 링크와 도착 지점 |

단순히 안내나 버튼이 존재하는지만 확인하지 않는다. 필요한 순간에 보이는지, 문구만으로 결과를 예상할 수 있는지, 과업을 마칠 수 있는지를 함께 판단한다. 익숙하지 않은 용어도 대상 사용자의 경험에 비춰 검토한다.

## 4. 점검 환경과 재현 조건

- 기본 화면: 데스크톱 1440×900, 모바일 390×844. 320px 폭은 긴 문구·줄바꿈·가로 넘침이 의심되는 화면을 추가 확인한다.
- 기본 흐름은 첫 방문 시 적용되는 테마로 끝까지 탐색한다. 이후 라이트·다크 테마의 소개 첫 화면, 개요, 대표 상세 화면을 비교한다.
- 별도 브라우저 세션 또는 초기화한 테스트 컨텍스트로 시작한다. 기존 테마·필터·데모 상태의 영향을 기록하고 반복 과업 전에 초기화한다.
- 데모는 기본 `attention`을 중심으로 전체 여정을 확인한다. `normal`, `empty`, `partial-failure`는 개요와 상태 변화가 드러나는 대표 화면을 확인한다.
- 키보드 Tab·Enter·Escape로 데모 진입, 메뉴 이동, 주요 상세 열기·닫기를 확인한다. 터치 화면에서는 hover 없이 같은 정보를 찾을 수 있는지 본다.
- 브라우저, URL, 화면 크기, 테마, 데모 상태, 관찰 시각을 모든 증거에 남긴다. 개발자 도구나 소스에서만 찾은 정보는 사용자에게 보이는 안내로 인정하지 않는다.

데모 상태 이름과 동작은 [시나리오 문서](../web/frontend/src/mocks/SCENARIOS.md), [선택기](../web/frontend/src/components/layout/DemoScenarioSwitcher.tsx)를 기준으로 확인했다. 선택기는 상태 변경 시 새로고침하므로 맥락을 잃거나 오류로 오해할 여지도 관찰한다.

## 5. 실행 순서와 과업

### 1단계 — 소개 페이지 첫인상

처음에는 스크롤과 추가 설명 없이 첫 화면을 관찰한다. 이어 아래 질문에 답을 뒷받침할 문구나 시각 요소가 있는지 기록한다.

- 이 서비스는 무엇을 해결하는가?
- 내가 쓰려면 어떤 환경이나 설치가 필요한가?
- 설치 전에 체험하려면 어디를 눌러야 하는가?

실사용자 테스트를 한다면 약 5초 노출 후 화면을 가리고 이해한 내용을 묻는다. 에이전트 점검에서는 이를 실제 사람의 5초 이해도 측정으로 보고하지 않고 첫 화면의 정보 검토로 기록한다.

### 2단계 — 소개 페이지에서 데모로 이동

과업: “설치하지 않고 제품이 어떻게 동작하는지 확인해 보세요.”

첫 클릭, 버튼을 찾기 위해 이동한 범위, 새 탭 전환 여부, 소개 화면과 데모의 시각·용어 일관성을 기록한다. 데모 URL로 바로 들어오는 경우도 별도 확인해 소개 페이지를 읽어야만 이해할 수 있는 부분을 찾는다.

### 3단계 — 데모에서 가치 발견

| 과업 | 완료 기준 | 중점 관찰 |
| --- | --- | --- |
| 지금 확인이 필요한 대상을 찾기 | 대상과 확인이 필요한 이유를 화면 근거로 설명한다 | 경고 표시, 정보 우선순위, 개요에서 상세로 가는 단서 |
| 오류 또는 느린 요청의 단서를 찾기 | 상세에서 관련 로그·요청·트레이스 중 원인을 좁힐 근거를 찾는다 | 메뉴 간 이동, 시간 범위와 대상 맥락, 차트·수치의 해석 |
| 원하는 정보를 메뉴에서 찾기 | 로그, API 요청, 서버 자원을 각각 어디서 찾는지 확인한다 | 메뉴 의미, 기능별 대상과 Docker 환경의 차이, 모바일 더보기 |
| 설치 방법으로 이동하기 | 데모 탐색 후 시작 문서를 찾고 첫 행동을 설명한다 | 문서 링크 발견, 돌아가기, 준비 조건과 실행 순서 |

관찰 전에 기대 이동 경로를 정답처럼 알려주지 않는다. 데이터 간 연계가 제공되지 않는 경우는 실패한 클릭으로 반복하지 않고, 안내와 대안 경로가 충분한지 기록한다.

### 4단계 — 상태별 이해와 회복

| 상태 | 과업 |
| --- | --- |
| 확인 필요 | 문제가 있는 대상과 다음 조사 행동을 찾는다. |
| 정상 운영 | 정상임을 이해하고, 확인할 문제가 없다는 상태를 빈 데이터와 구별한다. |
| 첫 시작 | 아직 대상이 없는 이유와 최초 등록·연결 방법을 찾는다. |
| 부분 수집 실패 | 서비스 장애와 수집 실패를 구별하고 재시도·설정 확인 경로를 찾는다. |

모바일에서도 데모 안내와 상태 선택기를 발견할 수 있는지 확인한다. 설정·추가 버튼은 데모에서 할 수 있는 범위와 결과가 어떻게 전달되는지 살펴본다. 예시 데이터로 실제 수집이나 알림 발송이 성공했다고 판정하지 않는다.

### 5단계 — 가독성·조작성 검토와 코드 대조

앞 단계에서 혼동이 생긴 지점을 우선 확인한다. 텍스트와 배경의 대비, 확대 시 읽기, 긴 서비스명과 줄바꿈, 색 이외의 상태 표현, 차트 단위·기간·범례, 포커스 표시, 모바일 화면 가림을 검토한다.

문구는 `toss-technical-writing`, UI 코드는 Vercel 기준과 프로젝트의 [DESIGN.md](../web/frontend/DESIGN.md)를 함께 참고한다. 외부 가이드의 문장부호나 표현 취향을 한국어 제품에 일괄 강제하지 않는다. 기존 디자인 규칙과 충돌하면 사용자의 과업에 미치는 영향을 근거로 대안을 제시한다.

코드 대조 대상:

- 소개와 행동 유도: [docs/index.md](../docs/index.md), `docs/.vitepress/theme/`
- 메뉴와 데모 안내: [navSections.ts](../web/frontend/src/components/layout/navSections.ts), [Sidebar.tsx](../web/frontend/src/components/layout/Sidebar.tsx), [DemoBanner.tsx](../web/frontend/src/components/layout/DemoBanner.tsx)
- 첫 화면과 상세: `web/frontend/src/pages/overview/`, `web/frontend/src/pages/capabilities/`, `web/frontend/src/features/healthcheck/`
- 사용 시작: [quickstart.md](../docs/guide/quickstart.md)

기존 [Playwright 설정](../web/frontend/playwright.config.ts)과 `web/frontend/e2e/`는 반복 동작 확인에 활용한다. 자동 테스트의 성공을 가독성이나 첫 방문 이해도 검증으로 대체하지 않는다.

## 6. 평가와 우선순위

과업별로 **도움 없이 완료 / 탐색·혼동 후 완료 / 미완료 / 검증 불가**를 기록한다. 첫 클릭, 잘못 들어간 경로, 되돌아간 횟수, 맥락을 잃은 지점을 함께 남긴다. 사람을 대상으로 측정하지 않은 수행 시간이나 성공률은 만들지 않는다.

| 우선순위 | 판단 기준 |
| --- | --- |
| P1 | 서비스의 용도·데모 상태를 크게 오해하게 하거나, 데모 진입·핵심 가치 경험·사용 시작을 막는다. |
| P2 | 과업은 가능하지만 정보를 찾기 어렵거나, 반복 탐색·추측·불필요한 읽기를 요구한다. |
| P3 | 과업 영향은 작지만 표현·여백·정렬·일관성을 개선할 수 있다. |

각 항목에 영향 범위, 수정 규모(S/M/L), 근거 확실성을 별도 기재한다. P1을 먼저 다루고, 같은 우선순위에서는 핵심 여정에 반복 등장하며 적은 수정으로 해소할 수 있는 문제를 먼저 선정한다.

근거는 `실행 관찰`, `코드 확인`, `사용자 검증 필요`로 구분한다. 객관적인 화면 잘림과 “용어가 어려울 것”이라는 해석을 같은 확실성으로 보고하지 않는다.

## 7. 산출물과 완료 조건

결과 보고서에는 다음 내용을 담는다.

1. 우선 개선할 항목 최대 5개와 선정 이유. 문제가 적으면 개수를 채우지 않는다.
2. 전체 발견 목록: 카테고리, 영향받는 과업, 우선순위, 근거 확실성, 수정 규모.
3. 각 발견의 화면 캡처·재현 단계·사용자 영향·구체적인 개선안·수정 후 확인 방법.
4. 문구 문제의 현재 문구와 수정안. 배치 문제는 필요할 때 간단한 전후 시안.
5. 정상적으로 작동해 유지할 요소와, 실행하지 못했거나 사람에게 확인해야 할 항목.

발견 기록 양식:

```text
ID / 카테고리 / 우선순위:
URL / 환경 / 데모 상태:
사용자의 과업:
재현 순서:
관찰 사실과 화면 근거:
사용자에게 미치는 영향:
근거 확실성: 실행 관찰 | 코드 확인 | 사용자 검증 필요
개선안 / 수정 규모:
수정 후 확인 방법:
관련 소스:
```

완료 조건은 기본 여정의 데스크톱·모바일 확인, 네 가지 데모 상태 확인, 주요 화면의 라이트·다크 검토, 모든 발견의 근거와 검증 방법 기록이다. 확인하지 못한 조건은 미검증으로 명시한다.

후속으로 실제 신규 사용자 3~5명에게 같은 과업을 수행하게 할 수 있다. 이 인원은 소규모 정성 확인을 위한 제안이며 통계적 성공률 추정용 표본이 아니다. 참여자는 별도 모집이 필요하고, 진행 전 메뉴나 정답 경로를 가르치지 않는다. 에이전트의 예상과 사람의 실제 반응은 분리해 기록한다.

이 계획의 실행 범위는 **배포된 소개 페이지와 데모의 첫 방문 여정을 관찰하고, 근거가 있는 개선 후보를 정리하는 것**이다. 구현과 시안 제작은 발견 항목을 정리한 후 필요한 범위를 결정한다.

## 8. 실행 기록 — 2026-11-07

발견 9건의 화면 근거·재현 단계·우선순위·개선안·수정 후 확인 방법은
