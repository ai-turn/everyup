# 서버 중심 화면 구조 설계

- 작성일: 2026-11-17
- 상태: 승인됨 (2026-11-17). Impeccable `critique`와 Hallmark `audit` 점검 결과를 6절과 8절에 반영했다.
- 화면 구성안: https://claude.ai/artifact/8vPCKhmHDprF4GxerSjeuD (비공개 캔버스, 화면 5장). 구성안은 디자인 점검 이전에 그린 것이므로, 이 문서와 다른 부분은 이 문서가 우선한다.
- 대체하는 결정: ADR 0007 (기능별 메뉴는 직접 설정 대상만 표시)

이 문서에서 "사용자 결정"이라고 표시한 항목은 사용자가 직접 정한 내용이고, "설계자 판단"이라고 표시한 항목은 설계 과정에서 채워 넣은 제안이다. 설계자 판단은 사용자가 언제든 바꿀 수 있다.

## 1. 의도

현재 EveryUp은 사이드바에서 업타임·로그·인프라·API 요청·메트릭을 기능별 메뉴로 나누고, 각 메뉴가 직접 설정한 대상의 목록과 상세 화면을 따로 가진다. 사용자는 모니터링을 "기능"이 아니라 "서버" 단위로 생각하는 편이 더 친근하다고 판단했다(사용자 결정). 서버 한 대를 열면 그 서버의 업타임, 인프라, 로그, API 요청, 메트릭을 한 화면에서 탭으로 관리하고, 진입 경로를 "서버"와 "Docker 환경" 두 갈래로 모으는 것이 이 개편의 목적이다.

비용이 크더라도 진행하기로 했고(사용자 결정), 세 가지 구현 방식 가운데 서버 엔티티를 신설하는 방식을 선택했다(사용자 결정, 4절 참조).

## 2. 목표, 비목표, 실패 조건

### 목표

1. 사이드바에서 기능별 메뉴 다섯 개를 없애고 `서버` 항목 하나로 대체한다.
2. 서버 목록 화면에서 어느 서버에 문제가 있는지, 그 원인이 무엇인지 한눈에 확인할 수 있다.
3. 서버 상세 화면의 탭에서 그 서버의 업타임·인프라·로그·API 요청·메트릭을 조회하고 연결한다.
4. 서버는 이름만 입력하면 만들 수 있고, 기능은 나중에 탭에서 하나씩 연결한다.
5. 기존에 직접 설정한 대상과 그 데이터는 하나도 유실되지 않고 서버 아래로 이전된다.
6. 기존 주소(`/uptime/:id`, `/logs/:id` 등)로 들어온 요청은 새 주소로 이동한다.

### 비목표

- Docker 환경 화면과 Docker Collector가 수집한 데이터는 변경하지 않는다. Docker 데이터는 계속 Docker 환경 화면에서만 보인다.
  - 후속(2026-11-19): 이 개편의 범위 밖에서 Docker 환경 상세를 서버 상세처럼 탭(개요·인프라·로그·API 요청)으로 나눴다. 데이터와 Docker 데이터의 위치는 그대로다. DESIGN.md §4.6 참고.
- 수집, OTLP 수신, 저장, 보존 기간, 알림 평가 경로는 변경하지 않는다. 알림 규칙은 지금처럼 개별 대상 ID를 가리킨다.
- 서버와 Docker 환경을 하나의 목록으로 합치지 않는다.
- API 요청 탭과 메트릭 탭에서 여러 앱의 데이터를 합쳐서 보여 주는 화면은 이번 범위에 넣지 않는다. 로그 탭만 서버 범위의 요약과 패턴을 제공한다(6.4절).
- 여러 서버에 걸친 업타임 모니터의 일괄 작업은 제공하지 않는다. 일괄 작업은 서버 하나의 업타임 탭 안에서만 동작한다(6.4절, 10절 4번).
- 서버 목록의 카드 보기는 제공하지 않고 그리드(비교 표)만 제공한다(설계자 판단).
- 서버 범위의 로그 검색과 수준 필터는 제공하지 않는다. 검색과 필터는 앱별 로그 상세 안에서 지금처럼 동작한다.
- 서버 단위 알림 규칙, 앱이 실행되는 호스트의 자동 판별, 사용하지 않게 된 `project_id` 컬럼의 삭제는 하지 않는다.
- 레거시 `services` 행(`type`이 `log` 또는 `icmp`)은 다루지 않는다.

### 실패 조건

기술적으로 동작하더라도 다음 중 하나에 해당하면 이 개편은 실패한 것으로 본다.

- 사이드바에 옛 기능별 메뉴와 서버 항목이 함께 남아 두 가지 탐색 구조가 공존한다.
- 마이그레이션 이후에 어느 서버에도 속하지 않은 직접 설정 대상이 남거나, 대상의 데이터가 사라진다.
- 서버 화면에 Docker Collector가 수집한 행이 나타난다.
- 서버를 만들기 위해 무언가를 먼저 설치하거나 연결해야 한다.
- `web/frontend/DESIGN.md`가 금지하는 표현이 새 화면에 들어간다. 여기에는 카드 좌측 상태 보더, 파스텔 틴트 박스, 붉은 위험 영역 카드, 3중 배지, 그리고 2026-11-15에 폐기한 "테두리 카드를 쌓아 놓은 화면"(§3.1)이 포함된다.

## 3. 제약

- 백엔드는 Go Fiber + SQLite(modernc, `CGO_ENABLED=0`)이며 연결 수가 1개(`SetMaxOpenConns(1)`)이므로, `rows.Next()` 반복문 안에서 다른 쿼리를 실행하면 교착 상태가 된다. 마이그레이션은 먼저 전체 행을 슬라이스로 읽은 뒤에 쓰기를 수행해야 한다.
- 마이그레이션은 재실행해도 안전해야 한다. 최신 버전은 `migrateV57`이므로 새 마이그레이션은 `migrateV58`이다(`web/backend/internal/database/migrations.go`).
- 프론트엔드는 한국어 전용이고 i18n 계층이 없다. 패키지 매니저는 pnpm만 사용한다.
- 디자인 규약의 정본은 `web/frontend/DESIGN.md`이다. 새 색·크기 값을 만들지 않고 기존 토큰과 공용 컴포넌트(`PageHeader`, `ResourceTable`, `StatusLight`, `EmptyState`, `Button`, `ChartCard`, `SummaryCard`)를 사용한다.
- `src/services/api/index.ts`는 배럴 파일이므로, 새 타입과 함수는 도메인 파일과 배럴 양쪽에 모두 추가해야 한다.
- `pnpm build`는 타입을 검사하지 않는다. 검증은 `pnpm lint`, `pnpm typecheck`, `pnpm build` 세 가지를 모두 실행해야 한다.
- 데모 e2e는 Pages 배포 과정에서만 실행된다. UI를 변경하는 PR은 머지 전에 로컬에서 `pnpm build:demo`와 `pnpm test:e2e`를 실행해야 하며, 4173/4174 포트를 다른 worktree의 서버가 점유하고 있는지 먼저 확인한다.
- main에 머지되는 PR은 각각 그 자체로 동작해야 한다. 쌓아 올린 PR은 base를 main으로 바꾼 뒤에 머지한다.

## 4. 검토한 방식

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 그룹을 서버로 승격 | 그룹 상세 화면에 기능별 탭을 추가하고 명칭을 바꾼다 | DB 변경이 없다 | 그룹에는 Docker 환경도 들어가므로 "서버 / Docker" 두 갈래와 충돌하고, 폴더 기능이 사라진다 |
| **B. 서버 엔티티 신설** | `servers` 테이블을 만들고 세 종류의 직접 대상이 서버에 소속된다 | Docker 환경과 대칭 구조가 되고, 그룹은 폴더로 남는다 | 백엔드와 프론트엔드 전반을 수정해야 한다 |
| C. Observed Service 중심 | 업타임 모니터와 인프라 리소스를 Observed Service에 연결한다 | Docker 서비스 상세 화면을 재사용하기 쉽다 | 서버 한 대에 앱이 여러 개 있으면 인프라의 소속이 모호해진다 |

사용자가 B를 선택했다. B에서는 직접 설정 대상이 서버의 그룹을 상속받는데, 이 규칙은 Docker에서 발견된 서비스가 Docker 환경의 그룹을 상속받는 기존 규칙(ADR 0003)과 동일하다.

## 5. 데이터 모델과 API

### 5.1 서버

서버는 사용자가 모니터링하는 단위이며, 보통 호스트 한 대 또는 배포 단위 하나를 의미한다. 서버는 다음 대상을 소유한다.

| 대상 | 저장 위치 | 서버당 개수 |
|---|---|---|
| 업타임 모니터 | `services` 테이블에서 `type IN ('http','tcp')`인 행 | 0개 이상 |
| 앱 (Direct Telemetry Connection이 있는 Observed Service) | `observed_services` | 0개 이상 |
| 인프라 리소스 (표준 OpenTelemetry Collector) | `hosts` 테이블에서 `collector_type = 'otel-collector'`인 행 | 0개 또는 1개 |

외부 URL처럼 호스트가 아닌 대상은 업타임 모니터만 가진 서버로 등록한다. 별도의 예외 처리는 두지 않는다(설계자 판단).

### 5.2 스키마 (`migrateV58`)

```sql
CREATE TABLE IF NOT EXISTS servers (
  id          TEXT PRIMARY KEY,           -- uuid
  name        TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  project_id  TEXT REFERENCES projects(id) ON DELETE SET NULL,
  created_at  DATETIME NOT NULL,
  updated_at  DATETIME NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_servers_name_group
  ON servers(lower(trim(name)), COALESCE(project_id, ''));
ALTER TABLE services          ADD COLUMN server_id TEXT REFERENCES servers(id);
ALTER TABLE observed_services ADD COLUMN server_id TEXT REFERENCES servers(id);
ALTER TABLE hosts             ADD COLUMN server_id TEXT REFERENCES servers(id);
CREATE UNIQUE INDEX IF NOT EXISTS idx_hosts_server_id ON hosts(server_id) WHERE server_id IS NOT NULL;
```

- 같은 그룹 안에서는 서버 이름이 고유하다(대소문자와 앞뒤 공백을 무시). 서로 다른 그룹에는 같은 이름의 서버가 있을 수 있고, 목록에서는 그룹 열로 구분된다. 이 규칙은 표현식 고유 인덱스로 DB가 보장한다.
- `server_id`의 외래 키에는 삭제 동작을 지정하지 않는다. 대상이 남아 있는 서버 행은 DB가 삭제를 거부하므로, 서버 삭제는 반드시 5.5절의 절차를 거친다.
- "서버당 인프라 리소스 최대 1개"는 부분 고유 인덱스로 DB가 보장한다.
- 그룹을 삭제하면 그 그룹의 서버는 그룹이 없는 상태가 된다. 이때 그룹이 없는 서버 가운데 같은 이름이 이미 있으면, 삭제되는 그룹에 있던 서버의 이름 뒤에 ` (2)`, ` (3)`을 붙여서 충돌을 피한다. 그룹 삭제가 이름 충돌 때문에 실패해서는 안 된다.
- 기존 대상 테이블 가운데 `services`와 `hosts`의 `project_id`에는 외래 키가 없어서 이미 삭제된 그룹을 가리키는 값이 남아 있을 수 있다. `observed_services`의 `project_id`에는 외래 키가 있지만, 외래 키 검사가 꺼진 상태에서 기록된 행에는 같은 문제가 있을 수 있다. 마이그레이션은 어느 테이블이든 존재하지 않는 그룹을 가리키는 값을 "그룹 없음"으로 취급한다.

### 5.3 불변식

**직접 설정 대상은 항상 서버 하나에 속한다.** `server_id` 컬럼은 `services`와 `hosts`가 다른 종류의 행도 담고 있어서 DB에서는 NULL을 허용하지만, 5.1절의 세 종류에 해당하는 행은 마이그레이션 이후 항상 값을 가진다. 이 불변식은 마이그레이션(5.4절)과 생성 API(5.5절)가 함께 보장한다.

**그룹 소속의 출처는 `servers.project_id` 하나이다.** 세 대상 테이블의 `project_id` 컬럼은 더 이상 읽지도 쓰지도 않는다. 대상 API 응답의 `projectId`는 소속 서버에서 조인하여 채운다. 그룹의 소속 대상 수(`GET /projects`)는 Docker 환경 수와 서버 수로 센다.

### 5.4 서버 찾기 규칙과 기존 데이터 이전

"이름과 그룹으로 서버를 찾고, 없으면 만든다"는 규칙 하나를 마이그레이션과 생성 API가 함께 사용한다.

1. (이름을 앞뒤 공백 제거 후 소문자로 바꾼 값, 그룹)을 키로 하여 기존 서버를 찾는다.
2. 같은 키의 서버가 있으면 그 서버에 연결한다.
3. 단, 대상이 인프라 리소스인데 그 서버에 이미 인프라 리소스가 있으면 이름 뒤에 ` (2)`, ` (3)`을 붙인 새 서버를 만든다.
4. 같은 키의 서버가 없으면 대상의 이름과 그룹을 그대로 가진 서버를 만든다.

`migrateV58`은 `server_id`가 비어 있는 직접 설정 대상을 인프라 리소스, 앱, 업타임 모니터 순서로 이 규칙에 따라 처리한다. 인프라 리소스를 먼저 처리하는 이유는 호스트 이름이 서버 이름으로 가장 적합하기 때문이다. 대상의 그룹은 기존 `project_id` 값을 사용한다. 전체 작업은 트랜잭션 하나로 수행한다.

결과적으로 이름과 그룹이 같은 대상들은 서버 하나로 묶이고, 나머지 대상은 대상 하나당 서버 하나가 된다(설계자 판단). 사용자는 이전 후에 대상을 옮기거나 서버를 합쳐서 정리할 수 있다(6.5절).

### 5.5 API

새 엔드포인트는 기존 대상 엔드포인트와 같은 인증 그룹에 둔다.

| 엔드포인트 | 동작 |
|---|---|
| `GET /servers` | 서버 목록. 필드는 `id`, `name`, `description`, `projectId`, `createdAt`, `updatedAt` |
| `POST /servers` | 생성. `name` 필수, `description`과 `projectId`는 선택. 같은 그룹에 같은 이름이 있으면 409 |
| `GET /servers/:id` | 단건 조회 |
| `PUT /servers/:id` | 이름, 설명, 그룹 변경. 이름 충돌은 409 |
| `DELETE /servers/:id` | 서버와 소속 대상을 모두 삭제 |
| `POST /servers/:id/merge` | 본문 `{ "targetServerId": "..." }`. 이 서버의 대상을 모두 대상 서버로 옮기고 이 서버를 삭제한다. 트랜잭션 하나로 수행하며, 두 서버가 모두 인프라 리소스를 가지고 있으면 409 |

기존 대상 엔드포인트(`/services`, `/observed-services`, `/infrastructure-resources`)의 변경 사항은 다음과 같다.

- 응답에 `serverId`를 추가하고, `projectId`는 서버에서 조인한 값으로 채운다.
- 생성 요청은 `serverId`를 받는다. `serverId`가 없으면 5.4절의 규칙으로 서버를 찾거나 만들어 연결한다. 존재하지 않는 `serverId`는 400으로 거부한다. 이 대체 동작 덕분에 프론트엔드 전환 전에도 불변식이 유지된다.
- 수정 요청에서 `serverId`를 바꾸면 대상이 다른 서버로 이동한다. 인프라 리소스를 이미 인프라 리소스가 있는 서버로 옮기는 요청은 409로 거부한다.
- 대상에 그룹을 직접 지정하던 경로(`PUT/DELETE /projects/:projectId/monitors/:monitorId`, 앱과 인프라 리소스 수정 본문의 `projectId`)는 제거한다. 다만 백엔드와 프론트엔드를 나누어 머지하는 동안에는 기존 화면이 깨지지 않도록, 이 경로들이 "대상이 속한 서버의 그룹을 바꾸는" 동작으로 유지되어야 한다. 구분 규칙은 다음과 같다. 앱과 인프라 리소스의 수정 본문에 `serverId`가 들어 있으면 새 화면의 요청으로 보고 `projectId`를 무시한다. `serverId`가 없으면 기존 화면의 요청으로 보고 본문의 `projectId`(비어 있으면 그룹 없음)를 그 대상이 속한 서버에 기록한다. 제거는 프론트엔드 전환이 끝난 뒤에 수행한다.
- 기존 화면에는 서버라는 개념이 없으므로, 기존 화면의 그룹 지정이 서버 이름 충돌 때문에 실패해서는 안 된다(최종 검토에서 발견된 설계 결함을 보완한 규칙이다). 옮겨 갈 그룹에 같은 이름의 서버가 이미 있으면 5.4절의 규칙대로 두 서버를 같은 서버로 보고 합친다: 대상이 속한 서버의 대상을 모두 그 서버로 옮기고 원래 서버를 삭제한다. 두 서버가 모두 인프라 리소스를 가지고 있어서 합칠 수 없으면, 옮기는 서버의 이름에 ` (2)`, ` (3)`을 붙이고 그룹을 바꾼다. 새 화면이 사용하는 서버 수정(`PUT /servers/:id`)의 이름 충돌은 지금처럼 409로 응답한다.
- 설정 파일(`config.json`의 `services`)로 등록되는 업타임 모니터처럼 API를 거치지 않고 만들어지는 직접 대상도 5.4절의 규칙으로 서버에 연결되어야 한다.
- `GET /projects`의 응답에 `serverCount`를 추가한다. 기존의 대상 종류별 개수 필드는 서버를 거쳐서 계산한 값으로 유지하다가, 프론트엔드 전환이 끝난 뒤에 제거한다.

서버 삭제는 소속 대상을 종류별 기존 삭제 경로(업타임 모니터 삭제와 상태 규칙 정리, 앱 삭제, 인프라 리소스 삭제)로 차례대로 지운 뒤에 서버 행을 지운다(설계자 판단). 기존 삭제 경로가 각자 트랜잭션을 가지고 있으므로 전체를 하나의 트랜잭션으로 묶지 않는다. 중간에 실패하면 서버와 남은 대상이 그대로 남고, 다시 삭제를 요청하면 이어서 진행된다.

서버 목록 화면에 필요한 상태와 수치는 새 집계 엔드포인트를 만들지 않고, 그룹 상세 화면이 지금 하는 방식대로 프론트엔드가 기존 엔드포인트의 결과를 `serverId`로 묶어서 구성한다(설계자 판단). 사용하는 엔드포인트는 대상 목록 3개와 `/logs/summary`이다. 24시간 가용률, 최근 체크, 진행 중인 장애는 업타임 모니터 목록 응답(`include=checks`)에, CPU와 메모리 사용률은 인프라 리소스 목록 응답에 이미 들어 있다. `/metrics/uptime-summary`는 일 단위 경계로 집계하므로 사용하지 않는다.

로그 요약과 패턴(`/logs/summary`, `/logs/patterns`)에는 `serverId` 필터를 추가한다. 현재 `/logs/patterns`의 조회 범위는 "Docker 환경 하나" 또는 "직접 연결 전체"뿐이고 상위 50건으로 잘라서 응답하므로, 서버 범위의 패턴은 프론트엔드에서 걸러 낼 수 없다. `serverId`가 주어지면 그 서버에 속한 앱의 로그만 집계한다.

## 6. 화면

**배치는 구성안을 따르고, 표현은 `DESIGN.md`를 따른다.** 구성안에 그려진 회색 표 헤더 띠, 테두리 카드, 알약 모양 탭, 상태색으로 칠한 상태 문구, 목록 화면의 제목과 설명 문구, 검은 채움의 주 버튼은 `DESIGN.md` §3.1, §3.4, §4.5, §4.6, §5.1과 어긋나므로 구현하지 않는다. 아래 각 절이 해당 부분을 어떻게 바꾸는지 적는다.

### 6.1 사이드바

```
개요
[모니터링 대상]  서버 · Docker 환경 · 그룹
[관리]          알림 · 환경 설정
```

업타임·로그·인프라·API 요청·메트릭 항목은 삭제한다. 사이드바 정의(`navSections.ts`)를 읽는 모바일 하단 내비게이션, 더보기 화면, 명령 팔레트, 헤더의 경로 표시도 함께 바뀐다. 모바일 하단에는 개요, 서버, 알림을 두고 나머지는 더보기에 둔다(설계자 판단). 장애 수 배지는 계산 방식과 위치를 모두 변경하지 않는다. 이 배지는 Docker 서비스의 장애도 포함하므로 지금처럼 개요 항목에 둔다. 구성안에서 서버 항목 옆에 그린 배지는 반영하지 않는다.

### 6.2 주소

| 주소 | 화면 |
|---|---|
| `/servers` | 서버 목록. 검색·상태·그룹 필터는 쿼리(`q`, `status`, `group`)에 둔다 |
| `/servers/new` | 서버 추가 |
| `/servers/:serverId` | 서버 상세, 개요 탭 |
| `/servers/:serverId/:capability` | 기능 탭. `capability`는 `uptime`, `infrastructure`, `logs`, `api`, `metrics` 중 하나 |
| `/servers/:serverId/:capability/:targetId` | 탭 안에서 특정 모니터 또는 앱을 선택한 상태 |

탭을 `?tab=` 쿼리가 아니라 경로로 표현하는 이유는, API 요청 화면의 `useRequestQuery`가 이미 `?tab=requests|traces`를 사용하고 있어서 이름이 겹치기 때문이다. 기존 탭 컴포넌트들이 사용하는 `pattern`, `traceId`, `range`, `view` 같은 쿼리는 그대로 유지한다.

기존 주소는 다음과 같이 이동시킨다.

| 기존 주소 | 이동할 주소 |
|---|---|
| `/uptime`, `/infrastructure`, `/api`, `/metrics`, `/services` | `/servers` |
| `/uptime/:monitorId` | `/servers/:serverId/uptime/:monitorId` |
| `/logs/:serviceId`, `/api/:serviceId`, `/metrics/:serviceId` | `/servers/:serverId/<기능>/:serviceId` |
| `/infrastructure/:resourceId` | `/servers/:serverId/infrastructure` |
| `/logs` | 6.6절 참조 |

상세 주소의 이동은 대상을 조회하여 `serverId`를 알아낸 뒤에 수행하며, 쿼리 문자열은 보존한다. 조회하는 동안에는 로딩 상태를 보여 주고, 대상을 찾지 못하면 서버 목록으로 가는 링크가 있는 안내 화면을 보여 준다. 서버가 만들어 내는 링크(개요 타임라인의 `targetPath` 등)는 새 주소로 바꾸고, 이미 발송된 알림에 들어 있는 옛 링크는 위 이동 규칙이 처리한다.

### 6.3 서버 목록 (구성안 1번)

**머리와 툴바.** 메뉴 첫 화면의 규칙(§3.4, §4.5 "목록 조작의 자리")을 그대로 따른다.

- 제목은 데스크톱에서 숨기고(`PageHeader menu`), 설명 문구는 두지 않는다. `새로고침`과 `서버 추가`는 헤더의 조작 자리에 두며, 크기와 모양은 헤더 기본값(작은 secondary 버튼)을 따른다.
- 툴바에는 왼쪽부터 검색, 상태 요약, 그룹 필터를 둔다. 상태 요약은 `장애, 확인 필요, 대기, 정상` 순서의 작은 수치 행이면서 동시에 상태 필터이다. 누르면 그 상태만 보이고(`?status=`, `aria-pressed`) 다시 누르면 해제된다. 구성안에 있던 별도의 상태 선택 상자는 두지 않는다.
- 검색은 서버 이름뿐 아니라 소속 대상의 이름과 주소까지 찾는다. 소속 대상이 일치한 경우에는 서버 이름 아래에 일치한 대상을 보여 준다(메트릭 목록의 선례).

**표.** 공용 `ResourceTable`을 사용하고, 바깥 카드 셸과 헤더 배경은 쓰지 않는다(§3.1).

- 열은 서버, 상태, CPU, 메모리, 업타임 24시간, 오류 로그 24시간, 그룹이다. 구성안에 있던 "수집 중인 기능" 열은 넣지 않는다. 이 열은 수치 열의 빈 값과 같은 내용을 반복하고, 한 줄에 가운뎃점을 여러 개 쓰게 되어 문구 규칙(§2.5)에도 어긋난다.
- 상태 칸은 `StatusLight`(점과 상태 문구)를 쓰고, 그 아래 줄에 가장 나쁜 대상의 원인을 보조 문구로 표시한다. 모니터와 앱의 원인 문구에는 대상 이름을 넣는다(예: "Checkout API 응답 없음, 3분째", "메모리 88%", "billing-api 데이터 대기 중"). 상태 문구를 상태색으로 칠하지 않는다(§5.1).
- 서버의 상태는 소속 대상들의 상태를 장애, 확인 필요, 정상, 대기의 순서로 합산한 값이다. 즉 "대기"는 모든 대상이 대기(일시정지, 비활성화, 상태 확인 중)이거나 대상이 하나도 없을 때에만 나오며, 정상인 대상이 하나라도 있으면 "정상"이다(구현 화면 점검에서 변경: 일시정지한 모니터 하나 때문에 서버 전체가 빈 서버처럼 보이는 문제). "대기"에도 원인 문구("연결한 대상 없음", "Checkout API 일시정지")를 표시한다. 대상별 판정은 그룹 화면이 사용하는 `projectMembers.ts`의 규칙(장애, 확인 필요, 대기, 정상)을 사용한다.
- 로그, API 요청, 메트릭의 기능별 상태는 수신 여부만 판정한 값이므로 "정상"이라고 쓰지 않고 수집 문구("수집 중", "데이터 대기 중", "연결 비활성화됨")로 표시한다. 오류 로그 건수 옆에 "정상"이 놓이면 안 되기 때문이다. 탭의 접근 가능한 이름과 개요 탭의 행이 같은 문구를 사용한다.
- 리소스 사용률도 상태에 반영한다(설계자 판단). 인프라 리소스의 CPU·메모리·디스크 사용률이 인프라 화면의 기존 경고 기준(`features/infra/usage.ts`의 `WARNING_PCT`, 70%) 이상이면 "확인 필요"로 판정하고, 사용률만으로는 "장애"로 판정하지 않는다. 기준을 넘은 수치 칸만 경고색 글자로 표시한다. 서버 목록, 서버 상세 개요, 그룹 화면은 모두 같은 판정 함수를 사용한다.
- 수집하지 않는 값은 0이 아니라 표의 빈 값 표시인 `-`로 쓰고, 접근 가능한 이름과 툴팁으로 "수집 안 함"임을 알린다(ADR 0009).
- 정렬은 상태가 나쁜 순서이고, 같은 상태 안에서는 이름순이다.
- 열의 배치는 뷰포트가 아니라 목록 컨테이너의 폭에 맞춘다(§4.5). 서버 이름과 상태, 원인은 항상 보이고, 폭이 좁아지면 그룹, 수치 열 순서로 숨긴다. 숨긴 수치는 서버 이름 아래로 옮겨서 페이지에 가로 스크롤이 생기지 않게 한다.
- 행은 제목 링크(`data-row-link`)로 서버 상세로 이동한다.

**상태별 화면.** 로딩, 서버 없음, 검색 결과 없음, 조회 실패의 네 가지 상태를 모두 구현한다. 서버가 하나도 없으면 서버 추가를 안내하고, Docker 환경이 있는 경우에는 그 데이터가 Docker 환경 화면에 있다는 점을 함께 알려 준다. 대상 목록 가운데 일부만 조회에 실패하면 해당 칸을 `-`로 두고, 일부 정보를 불러오지 못했다는 안내와 다시 시도 버튼을 보여 준다.

### 6.4 서버 상세 (구성안 2~4번)

**머리말.** 헤더의 경로 표시는 `서버 › web-01`이고, 특정 대상을 선택한 주소에서는 `서버 › web-01 › 대상 이름`이 된다. 탭은 위치가 아니므로 경로에 넣지 않는다(§3.4). 모바일에는 헤더의 경로 표시가 없으므로 대상 화면에 `← 목록으로` 버튼을 둔다. 본문 머리에는 서버 이름(h1), 설명(있는 경우 한 줄), `StatusLight`, 원인 문구, 그룹을 두고, 조작으로는 새로고침과 서버 설정을 둔다. 원인 문구는 문제가 있는 대상의 주소로 연결되는 링크이다. 구성안에 있던 머리말의 조회 기간 선택은 두지 않는다. 기간은 각 패널이 지금처럼 자기 쿼리(`range`)로 관리한다.

머리말의 배치(기능 탭의 디자인 점검에서 확정): 새로고침과 서버 설정은 서버 이름과 같은 줄의 오른쪽에 두고, 그룹은 상태 줄의 한 항목으로 둔다. 상태 줄의 오른쪽 끝에는 서버 데이터를 마지막으로 성공해서 불러온 시각과 `30초마다 자동 갱신` 스위치를 둔다. 새로고침과 자동 갱신은 서버 수준에 하나씩만 있고, 열려 있는 패널의 데이터도 함께 제어한다. 머리말의 높이는 모든 탭에서 같다. 탭 줄의 오른쪽 끝은 현재 탭의 조작 자리이며, 대상을 추가하는 버튼(`모니터 추가`, `로그 연결`, `API 연결`, `메트릭 연결`)을 여기에 둔다.

패널의 배치(같은 점검에서 확정): 패널은 대상 이름을 h2 한 줄로 표시하고 수정·삭제·옮기기를 그 줄의 오른쪽에 둔다. 상태를 켜고 끄는 조작은 상태 표시 옆에 두고, 기간 선택은 상태 줄의 오른쪽에 둔다. API Key 같은 연결 정보는 접어 둔다. 목록이 있는 탭(업타임, 로그)의 대상 상세에는 `모니터 목록`, `앱 목록` 링크를 두며, 이 링크는 목록의 검색어와 필터와 보기 방식을 유지한 채로 돌아간다. 서버 화면에서는 대상을 "앱"이라고 부르고 "서비스"와 "메뉴"라는 말을 쓰지 않는다.

조회 실패의 처리: 대상 목록 하나의 다시 불러오기가 실패하면 이전에 불러온 목록을 유지하되, 그 기능의 상태는 현재의 상태처럼 보여 주지 않고 `확인 불가`로 표시한다. 이전 목록도 없으면(첫 조회의 실패) 불러오지 못했다는 안내를 보여 준다.

**탭.** 탭은 패널을 바꾸므로 `role="tablist"`의 밑줄 탭을 쓴다(§4.6). 구성안의 알약 모양 탭은 쓰지 않는다. 탭 줄은 줄바꿈하지 않고 한 줄에서 가로로 스크롤하며, 구현은 `AgentServiceTabs`의 `TabBar` 방식을 `components/common`의 공용 컴포넌트로 옮겨서 서버 상세와 Docker 서비스 상세가 함께 사용한다.

- 탭 이름 옆에 대상 수를 숫자로 표시하지 않는다. 숫자가 오류 건수로 읽히기 때문이다. 대상 수는 접근 가능한 이름에 담는다(예: "업타임, 모니터 2개, 장애").
- 장애 또는 확인 필요 상태인 기능의 탭에는 이름이 있는 상태 점(§5.2)을 붙인다. 알림 링크나 옛 주소로 다른 탭에 바로 들어온 사용자도 어느 기능에 문제가 있는지 알 수 있어야 하기 때문이다.
- 연결되지 않은 기능의 탭은 흐린 글자와 "연결 전" 보조 문구로 표시한다.
- 이미 선택된 탭을 다시 누르면 그 탭의 첫 화면(대상 목록 또는 기본 대상)으로 돌아간다.

**개요 탭.** 구성안의 같은 무게 카드 5장은 쓰지 않는다. 페이지 섹션은 카드로 감싸지 않는다는 규칙(§3.1)에 따라 다음과 같이 구성한다.

- 진행 중인 장애가 둘 이상이면 가장 위에 상태 배너로 표시하고, 장애가 난 대상마다 그 대상으로 바로 가는 링크를 나열한다. 장애가 하나이면 머리말의 원인 링크가 같은 내용을 보여 주므로 배너를 두지 않는다(구현 화면 점검에서 변경: 장애 하나가 화면에 네 번 표시되는 문제). 깜빡이는 점은 머리말에만 둔다.
- 그 아래에 연결된 기능을 섹션 행으로 나열한다. 각 행은 기능 이름, `StatusLight`, 수치 두세 개, 해당 탭으로 가는 링크로 구성하고, 문제가 있는 기능을 위에 둔다. 업타임 행에는 최근 체크 띠(`RecentUptimeChecks`)를 넣어 시간 흐름을 보여 준다.
- 연결되지 않은 기능은 맨 아래 섹션 하나에 모아 텍스트 버튼으로 제공한다.
- 대상이 하나도 없는 서버에서는 `EmptyState` 하나만 보여 준다. 주 버튼은 설치가 필요 없는 "업타임 모니터 추가"이고, 나머지 네 기능은 보조 버튼으로 둔다.

**기능 탭.** 기존 메뉴별 상세 화면의 본문을 탭 안에서 재사용한다. 현재 `Direct*DetailPage`와 `UptimeMonitorDetailPage`는 주소에서 ID를 직접 읽고 삭제 후에 옛 메뉴 주소로 이동하므로, 각각을 `{ 대상 ID, 삭제 후 처리 }`를 props로 받는 패널 컴포넌트로 바꾸고 페이지 파일은 삭제한다. 대상별 연결 정보, 키 재발급, 연결 해제 같은 기존 동작은 패널 안에 그대로 남는다.

| 탭 | 대상이 없을 때 | 1개일 때 | 2개 이상일 때 |
|---|---|---|---|
| 업타임 | 연결 안내 | 그 모니터의 상세 | 모니터 목록을 보여 주고, 선택하면 상세로 이동 |
| 인프라 | 연결 안내 | 그 리소스의 상세 | 해당 없음 |
| 로그 | 연결 안내 | 서버 범위의 요약과 패턴, 앱 목록. 앱을 선택하면 그 앱의 로그 상세로 이동 | 왼쪽과 같음 |
| API 요청, 메트릭 | 연결 안내 | 그 앱의 상세 | 앱 선택 컨트롤과 선택한 앱의 상세 |

- 업타임 탭의 모니터 목록은 현재 `/uptime` 목록의 본문(상태 필터, 보기 전환, 선택 후 일괄 일시 중지·삭제, 최근 체크)을 서버 범위로 좁혀서 그대로 사용한다. 따라서 일괄 작업은 서버 하나 안에서만 동작한다.
- 로그 탭은 서버에 속한 모든 앱의 오류·경고 수와 패턴 표를 먼저 보여 준다. 현재 전체 로그 화면의 본문(`LogServiceOverview`)을 서버 범위로 좁혀서 재사용하며, 5.5절의 `serverId` 필터가 이를 지원한다. 패턴 표에서 항목을 선택하면 해당 앱의 로그 상세로 이동하면서 `?pattern=` 필터를 전달한다. 구성안 3번에 그려진 서버 범위의 검색창, 수준 필터, "전체 앱" 선택 버튼은 넣지 않는다.
- API 요청 탭과 메트릭 탭의 앱 선택 컨트롤은 선택지마다 상태 점을 표시하고, 기본 선택은 첫 번째 앱이 아니라 상태가 가장 나쁜 앱이다. 첫 번째 앱을 기본값으로 두면 장애가 난 다른 앱이 가려지기 때문이다. 여러 앱을 합친 화면은 제공하지 않는다(설계자 판단). 요청 통계와 메트릭은 앱마다 엔드포인트와 지표 이름이 달라서 합산한 수치의 의미가 불분명하다.

**연결 안내 (구성안 4번).** 연결되지 않은 탭은 `EmptyState`에서 무엇이 필요한지 안내하고, 기존 설정 대화 상자(`UptimeMonitorDialog`, `DirectTelemetrySetupDialog`, `InfrastructureCollectorSetupDialog`)를 `serverId`와 함께 연다. 구성안에 있던 "개요로 돌아가기" 버튼은 바로 위의 개요 탭과 중복되므로 두지 않는다. 생성이 끝나면 해당 대상의 주소로 이동하고, 포커스를 패널의 제목으로 옮기며, 토스트로 결과를 알린다. 대상이 이미 있는 탭에서도 같은 대화 상자로 모니터나 앱을 추가할 수 있다. 이미 등록된 앱에 신호를 추가하는 기능이 현재 대화 상자에 있으면 그대로 사용하고, 없으면 새 앱을 추가하는 경로만 제공한다. 안내 문구는 실제로 제공하는 동작만 설명한다.

### 6.5 서버 추가, 대상 이동, 서버 합치기 (구성안 5번)

- **서버 추가.** 이름, 설명, 그룹만 입력받는다. 구성안 5번에 있던 "수집할 기능" 체크박스는 넣지 않는다(설계자 판단). 서버를 만들면 개요 탭으로 이동하고, 그 화면이 같은 선택지를 연결 버튼으로 제공하므로 여러 단계를 차례로 여는 흐름을 따로 만들 필요가 없다. 같은 그룹에 같은 이름의 서버가 있으면 입력란 아래에 바로 알려 준다.
- **대상 이동.** 각 대상의 설정에 "다른 서버로 옮기기"를 둔다. 인프라 리소스를 옮길 때는 이미 인프라 리소스가 있는 서버를 선택지에서 비활성으로 표시하여 충돌을 미리 막는다.
- **서버 합치기.** 서버 설정에 "다른 서버 합치기"를 둔다. 다른 서버를 여러 개 선택하면 그 서버들의 대상을 모두 이 서버로 옮기고 선택한 서버들을 삭제한다(구현 화면 점검에서 방향을 변경: 이 서버를 다른 서버 하나로 보내는 방식은 정리할 서버마다 한 번씩 왕복해야 했다). 마이그레이션으로 생긴 대상 하나짜리 서버들과 빈 서버들을 한 번에 정리하기 위한 기능이며, 실행 전에 옮겨질 대상의 합계와 삭제될 서버의 수를 보여 준다. 인프라 리소스는 서버마다 하나이므로 충돌하는 서버는 선택지에서 비활성으로 표시한다. API는 선택한 서버마다 `POST /servers/:id/merge`를 차례로 호출하며, 중간에 실패하면 멈추고 결과를 알린다.
- **서버 삭제.** 서버 설정에 두고, 확인 창의 제목에 서버 이름을 넣고 함께 삭제될 대상의 종류와 개수를 보여 준다. 대상 목록을 불러오지 못한 상태에서는 "대상이 없다"고 단정하지 않는다. 삭제한 뒤에는 사용자가 보던 검색 조건의 서버 목록으로 돌아간다. 위험 동작의 표현은 기존 규칙(중립 표면에 붉은 글자의 조작)을 따른다. 서버 설정 대화 상자에서 합치기와 삭제는 입력란 아래, 저장 줄 위에 둔다.
- 대상을 모두 옮겨서 비게 된 서버는 자동으로 삭제하지 않는다. 대상이 없는 서버는 서버 목록에서 "대기" 상태로 보이며, 사용자가 상태 필터로 찾아서 삭제한다. 백엔드만 배포된 기간에 기존 화면에서 마지막 대상을 삭제하여 생긴 빈 서버도 같은 방식으로 정리한다(설계자 판단).

### 6.6 여러 서버를 가로지르는 화면

- 개요 화면은 계속 서버와 Docker 환경의 장애를 함께 보여 주고, 대상 링크만 새 주소로 바꾼다.
- 그룹 화면의 구성원은 Docker 환경과 서버가 되고, 장애 상태인 Docker 서비스는 지금처럼 함께 표시한다. 그룹에 대상을 추가하는 대화 상자는 Docker 환경과 서버만 다룬다.
- 알림 규칙 화면에서 대상을 고를 때 대상 이름 앞에 서버 이름을 함께 표시한다. 그 밖의 알림 동작은 변경하지 않는다.
- 전체 로그 화면(`/logs`)은 사이드바에서는 빠지지만 화면 자체는 "전체 로그"라는 이름으로 남기고, 개요 화면과 명령 팔레트에서 들어갈 수 있게 한다(설계자 판단). 장애가 어느 서버에서 발생했는지 모르는 상황에서는 서버를 가로지르는 로그 요약과 패턴이 필요하기 때문이다. 각 행은 서버 이름을 함께 표시하고 해당 서버의 로그 탭으로 연결된다. 내비게이션에서는 서버 섹션에 속한 화면으로 취급하여, 이 화면에서는 사이드바의 `서버`가 현재 위치로 표시된다. 업타임·인프라·API 요청·메트릭의 전체 목록은 서버 목록이 대신하므로 남기지 않는다.

### 6.7 모든 새 화면에 적용되는 규칙

디자인 점검에서 확인된 사항이며, 새로 만드는 화면 전체에 적용한다.

- **데이터 영역의 네 가지 상태.** 서버 목록, 개요 탭의 섹션, 각 탭의 목록은 로딩, 비어 있음, 검색 결과 없음, 오류 상태를 모두 가진다. 조회에 실패했을 때 이전 데이터가 있으면 이전 정보임을 표시하고 유지한다.
- **상태는 주소에 둔다.** 검색어, 필터, 선택한 앱, 보기 방식은 쿼리나 경로에 담아서 새로고침과 링크 공유 후에도 유지되게 한다.
- **좁은 화면.** 320px 폭에서도 페이지에 가로 스크롤이 생기지 않아야 한다. 표는 열을 숨기고 값을 이름 아래로 모으며, 탭 줄만 자체적으로 가로 스크롤한다. 모바일에서 누르는 대상의 높이는 44px 이상이다(§4.1).
- **문구.** 한 줄에 띄어 쓴 가운뎃점은 하나까지만 쓰고, 같은 종류의 나열은 쉼표로 잇는다. 줄표는 쓰지 않고, 말줄임은 `…` 문자를 쓴다(§2.5, ADR 0009). 기술 용어는 `DESIGN.md` §9.15의 표기를 따른다(예: `Endpoint`).
- **접근성.** 상태를 색만으로 전달하지 않는다. 문구가 없는 상태 점에는 이름을 준다(§5.2). 탭, 앱 선택, 필터는 키보드로 조작할 수 있어야 하고, 화면이 바뀐 뒤의 포커스 위치를 정해 둔다.

## 7. 함께 바뀌는 것

- **용어집과 결정 기록.** `CONTEXT.md`에 Server를 추가하고 Capability Menu 항목을 서버의 기능 탭 설명으로 바꾸며, Group의 정의를 "Docker 환경과 서버를 묶는 폴더"로 고친다. Docker Environment 항목의 "server라고 부르지 말 것"은 유지한다. ADR 0011을 새로 작성하여 ADR 0007을 대체하고, ADR 0003(그룹 상속)과 ADR 0004(업타임 모니터와 인프라 리소스는 별도 모듈)에 서버 소속 규칙이 추가되었음을 기록한다. ADR은 기존 관례대로 영어로 작성한다.
- **디자인 규약.** `web/frontend/DESIGN.md`에서 메뉴를 전제로 한 서술을 서버 화면 기준으로 고치고, 공용 탭 컴포넌트와 서버 목록·상세의 규칙(6.3절, 6.4절)을 해당 절에 기록한다.
- **데모와 mock 데이터.** `services/mockRouter.ts`와 `mocks/demoTargets.ts`에 서버를 추가하고 모든 직접 대상에 `serverId`를 부여한다. 데모 시나리오에는 여러 기능이 연결된 서버, 일부 기능만 연결된 서버, 업타임만 있는 외부 대상, 대상이 없는 서버가 모두 포함되어야 한다.
- **e2e 테스트.** 메뉴 주소를 사용하는 spec(약 35개)을 새 주소에 맞게 고치고, `capability-menus.spec.ts`는 서버 목록과 탭을 검증하는 spec으로 교체한다.
- **문서.** `docs/guide`와 `docs/en/guide`의 관련 문서, `capture-screenshots.mjs`의 촬영 목록과 `docs/index.md`의 캐러셀을 갱신한다.
- **사용하지 않게 되는 코드.** 메뉴별 목록 페이지, `Direct*DetailPage`, 메뉴를 전제로 한 프로토타입 파일(`UptimeList.prototype.tsx` 등)은 삭제한다.

## 8. 작업 순서와 검증

main에는 다음 세 묶음을 차례로 머지한다. 사이드바에 옛 메뉴와 서버가 함께 보이는 중간 상태는 main에 올리지 않는다.

1. **백엔드 기반.** `migrateV58`, 서버 API, 대상 API의 `serverId`, 로그 요약·패턴의 `serverId` 필터, 그룹 수 집계 변경, ADR 0011과 `CONTEXT.md`. 이 묶음만 머지된 상태에서도 기존 화면은 그대로 동작해야 한다.
2. **프론트엔드 전환.** 서버 화면, 탭, 추가·이동·합치기, 사이드바 교체, 주소 이동, 그룹·개요·알림·명령 팔레트 수정, mock 데이터, e2e. 이 묶음이 가장 크다.
3. **정리.** 사용하지 않는 엔드포인트와 코드 삭제, 사용자 문서와 스크린샷 갱신.

묶음마다 통과해야 하는 검증은 다음과 같다.

- **백엔드**: `CGO_ENABLED=0 go test ./...`. 추가할 테스트는 마이그레이션(이름 병합, 인프라 리소스 충돌 시 이름 접미사, 재실행 안전성, 데이터 보존), 서버 CRUD와 이름 충돌 409, `serverId` 없이 대상을 만들 때의 서버 찾기·생성, 대상 이동과 409 응답, 서버 합치기, 서버 삭제 시 소속 대상과 데이터 삭제, 로그 요약·패턴의 `serverId` 필터이다.
- **프론트엔드**: `pnpm lint`, `pnpm typecheck`, `pnpm build`, `pnpm build:demo` 후 `pnpm test:e2e`.
- **디자인 점검**: UI를 변경하는 작업은 아래 검사를 통과한 뒤에 다음 작업으로 넘어간다. 두 스킬은 원본 저장소의 `C:/dev/mt-app/.claude/skills/`에 설치되어 있다.
  - Impeccable 정적 검사(`web/frontend`에서 실행): `node C:/dev/mt-app/.claude/skills/impeccable/scripts/detect.mjs --json src`
  - Hallmark 정적 검사(`web/frontend`에서 실행): `node C:/dev/mt-app/.claude/skills/hallmark/scripts/sloplint.mjs src --scope app --genre modern-minimal --json`. 작업을 시작하기 전에 기준선을 측정해 두고, FAIL과 WARN이 기준선보다 늘지 않아야 하며 가운뎃점 규칙(gate 63)이 새로 검출되지 않아야 한다. 판정은 종료 코드가 아니라 출력의 요약으로 한다.
  - Hallmark 렌더링 검사: 데모 빌드를 로컬 서버로 띄운 뒤, 같은 명령에 `--render`와 새 화면의 `--url`(서버 목록, 개요 탭, 로그 탭, 연결 전 탭, 서버 추가)을 지정하여 실행한다. 가로 넘침(34), 줄바꿈된 링크(49b), 화면 밖 표 열(F25), 대비(40) 항목이 0건이어야 한다. 실행에는 `HALLMARK_PUPPETEER`와 `CHROME_PATH` 환경 변수가 필요하다.
  - 묶음 2의 마지막에 구현된 화면을 대상으로 Impeccable `critique`를 다시 실행하여, 이번 점검의 우선 문제 다섯 가지가 해소되었는지 확인한다.
- **화면 확인**: 새 화면을 라이트·다크 테마와 데스크톱·모바일 폭에서 실제로 열어서 확인한다.

## 9. 구현자에게 맡기는 것

- Go와 TypeScript의 파일·함수·컴포넌트 이름과 분할 방식. 기존 관례(`repository_{entity}.go`, `services/api/{entity}.ts`, `features/{domain}/`)를 따른다.
- 서버 목록에서 상태와 수치를 구성하는 훅의 구조, 그리고 `projectMembers.ts`와 공유할 상태 판정 함수의 위치.
- 공용 탭 컴포넌트의 세부 모양과, Docker 서비스 상세 화면을 이 컴포넌트로 옮기는 시점.
- 서버 목록의 열을 숨기는 컨테이너 폭의 정확한 기준값. `ResourceTable`과 업타임 목록의 기존 기준을 따른다.
- 서버 상세 개요 탭의 섹션 행에 표시할 수치의 정확한 구성. 기존 엔드포인트가 제공하는 값만 사용한다.
- API 요청 탭과 메트릭 탭의 앱 선택 컨트롤의 종류. 앱이 적을 때는 `SegmentedControl`, 많을 때는 선택 상자를 쓰는 식으로 정한다.
- 묶음 2를 몇 개의 작업으로 나눌지와 그 순서.
- 저장소 루트의 `e2e/monitoring-target`이 메뉴 주소에 의존하는지에 대한 확인과 수정.

## 10. 설계자 판단으로 확정한 결정

아래 네 가지는 사용자에게 확인을 요청했고, 별도의 답이 없어 설계자 판단대로 진행한다. 구현 도중에도 바꿀 수 있다.

1. **전체 로그 화면을 남길지** (6.6절). 사이드바 밖에 "전체 로그"로 남긴다.
2. **기존 대상을 서버로 이전하는 규칙** (5.4절). 이름과 그룹이 같은 대상을 서버 하나로 묶고, 나머지는 대상 하나당 서버 하나로 만든다.
3. **서버 삭제 시의 동작** (5.5절, 6.5절). 확인 창에서 삭제될 대상을 보여 준 뒤에 소속 대상과 데이터를 모두 삭제한다. 대안은 대상이 남아 있으면 삭제를 막는 것이다.
4. **여러 서버에 걸친 업타임 일괄 작업** (6.4절). 제공하지 않는다. 지금은 `/uptime` 목록에서 모든 모니터를 한 번에 선택하여 일시 중지하거나 삭제할 수 있지만, 개편 후에는 이 작업이 서버 하나의 업타임 탭 안에서만 가능하다. 이전 직후에는 대부분의 모니터가 서버 하나에 하나씩 들어가므로 사실상 한 번에 하나씩 처리하게 된다. 디자인 점검에서도 업타임 위주로 사용하는 사용자에게는 후퇴라는 지적을 받았다. 대안은 서버 목록에 카드 보기와 선택 후 일괄 일시 중지·삭제를 추가하는 것이다.
